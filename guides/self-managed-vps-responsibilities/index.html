What You Manage on a Self-Managed VPS

We earn commissions when you shop through the links below.

The work behind a self-managed VPS: updates, access control, backups, recovery, and monitoring, and why the low monthly price leaves this to you.

Updated Oct 15, 2026

With a self-managed VPS, nobody steps in after the server boots up. Getting a website online is the beginning: someone has to keep the software updated, protect access, notice failures, and bring the site back when something breaks.

The self-managed plans in our price tables start at $3.50 a month (Vultr Cloud Compute 0.5 GB, checked 2026-10-08) and $4 a month (DigitalOcean Basic 512 MiB, checked 2026-10-01). That price covers the virtual server. The work below is not included.

The provider runs the physical hardware and the virtualization platform. You are usually responsible for the operating system, installed software, your application, and its configuration. The exact boundary is in the service agreement. [1]

Keep the system and application updated

Pick an operating system release that still receives security updates, and note its end-of-support date. Update the operating system and everything you install: web server, runtime, database, and application dependencies. Some updates need a restart.

After updating, check that the site's important functions still work. Automatic security updates reduce routine work, but you still need to configure their restart behavior and watch for failures. [2]

Protect access

Turn on multi-factor authentication for the hosting account. Give each administrator their own access, limit privileges, and remove access that is no longer needed. Use a secure SSH authentication method and protect the keys.

Only expose the services that need to be public. Keep databases and admin panels off the open internet unless you have a specific reason and proper protection. Before tightening remote-access settings, make sure another recovery route works so you do not lock yourself out.

Keep passwords and API keys out of public code and web-accessible folders. [4]

Backups only count if you can restore them

Decide what to save (database, uploaded files, configuration), how often, where the copies live, and how long to keep them. A server snapshot can help, but it may not give you a consistent copy of a busy database.

Keep a copy away from the running server, and test restoring it somewhere separate. Decide how much recent data you can afford to lose and how long the site can be down; those answers set your backup schedule. [3] Write the restore steps down while the site is healthy. Even on shared hosting, I still download my own backups rather than relying entirely on the host.

Watch the site from outside

Monitor memory, CPU, disk space, application errors, and backup results. Also check the site from outside the server, so you notice failures the server cannot report itself. Automate certificate renewal and make sure failures reach an inbox you actually check [5], and keep track of your domain renewal date. [4]

A short checklist before you rely on the server

  • Who handles updates, access changes, and urgent problems
  • Where backups are stored and when a restore last worked
  • Which alerts are on and who receives them
  • How to get back in, or rebuild, if the server fails
  • Which resources keep billing during an outage

A self-managed VPS makes sense when you have the skills, the time, or reliable help. If nobody can own these tasks, compare it with shared hosting, where the host handles more of this for you.
