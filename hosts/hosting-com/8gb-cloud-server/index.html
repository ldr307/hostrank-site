Who this plan suits

This plan is aimed at store owners who want hosting.com to handle the server itself. The features list it as a fully managed server, which means the day-to-day server administration is the provider's responsibility rather than the shop owner's. For someone whose time is better spent on products, orders and customers than on server maintenance, that is the main reason to look at a managed plan instead of an unmanaged one.

The plan also lists Unlimited websites, so a store that runs a main shop alongside a blog, a landing page or a second storefront can keep them on the same server. With 4 dedicated CPU cores and 8 GB dedicated memory, the resources are reserved for this server rather than shared with other customers, which matters for a store where checkout pages must keep responding during a sale or a promotion.

Store owners who are comfortable paying a full year upfront and who expect their store to stay on this plan for the whole term are the readers this plan fits most naturally. Anyone who prefers to pay month to month and walk away at any time should read the billing section carefully before signing up.

Resources listed on the official pricing page

The official data lists three resource figures for this plan: 4 dedicated CPU cores, 8 GB dedicated memory and 150 GB NVMe. The word dedicated appears on both the CPU and memory lines, which in hosting terms usually describes resources assigned to a single server rather than pooled across many customers.

Storage is listed as 150 GB NVMe. For a store, storage is used by product images, order records, the database, email mailboxes and the backup copies the provider keeps, so it is worth estimating how much a catalog and its images will take up before choosing between this plan and a larger or smaller size.

The official data does not list a bandwidth or data transfer figure for this plan. A store with heavy image traffic or large downloads should confirm with hosting.com whether there is a transfer limit before signing up.

HTTPS on the checkout page

A checkout page must load over HTTPS. Browsers warn visitors about forms on unencrypted pages, payment processors generally require an encrypted connection, and customers notice the padlock. The official data lists emails and security included, but it does not spell out whether that wording covers an SSL or TLS certificate for the store's domain. Before signing up, confirm with hosting.com that a certificate is included, how it is issued and whether it renews automatically.

Once the store is live, a quick way to confirm the certificate is working from any computer is to request the response headers over HTTPS and check that the request succeeds without a certificate warning: curl -I https://example.com. Replace example.com with the store's own domain. The output should show a successful response and, ideally, a redirect from the plain HTTP address to the HTTPS one, so that no visitor can land on an unencrypted version of the checkout.

Store owners should also check that every page in the purchase path, not only the home page, loads over HTTPS without mixed-content warnings. Images, scripts or payment widgets loaded over plain HTTP on an otherwise secure page can break the padlock on exactly the page where it matters most.

Backups and restoring an order database

The features list daily backups included. For a store, the database holds orders, customer accounts and stock levels, so a daily backup limits how much of that history could be lost if something goes wrong with a plugin update, a theme change or a mistaken bulk edit.

The data does not describe how long backups are kept, whether a store owner can restore a single file or database on their own, or whether a restore requires a support request. Those answers decide how quickly a broken checkout can be put back, so confirm them with hosting.com before relying on the included backups as the only safety net.

Many store owners also keep an independent copy of their database and product images outside the host, downloaded before any major change. This is not something the data describes or includes; it is simply a common habit that does not depend on the provider.

Practical setup guide

  1. STEP 1Build the store before changing any DNS

    After signing up, install the store platform, add the products, configure the payment gateway in test mode and place a trial order while the site is still reachable only through the temporary address the provider gives. Do not move the domain yet. Nothing should point customers at the new server until a test checkout completes from start to finish.

  2. STEP 2Connect the domain

    If the store uses the free domain registration included in the plan, the domain is registered through hosting.com; otherwise update the nameservers or DNS records at the current registrar to point at the new server, following the provider's instructions. To confirm which nameservers the domain currently uses from any computer, run this and replace example.com with the store's domain: dig +short NS example.com. DNS changes take time to spread, so keep the old site live until the new one answers everywhere.

  3. STEP 3Enable HTTPS and force it on every page

    Once the domain resolves to the new server, enable the certificate for the store's domain. The data lists emails and security included but does not name a certificate specifically, so if it is not available in the account, ask hosting.com how to add one. Set the store to redirect every plain HTTP request to HTTPS and walk through the full purchase path checking for the padlock and for mixed-content warnings on the cart and checkout pages.

  4. STEP 4Learn how the daily backups restore

    The plan lists daily backups included, but the data does not describe retention or whether a store owner can restore files or the database without a support request. Ask hosting.com how a restore works and how long it takes before the store depends on it. Many store owners also download a copy of the database and product images before any major update as an extra safeguard, which is a habit independent of the provider.

  5. STEP 5Record the renewal date and the renewal price

    The plan is priced in USD per month on a 1-year term, paid upfront, with a 12 months term, and the renewal rate is higher than the first-term rate. Write the renewal date in the store's calendar with a reminder a few weeks ahead, and note the renewal price from the table on this page so the second year's cost is already in the budget. Keep the provider's answers about cancellation, refunds and domain ownership in the same place.
