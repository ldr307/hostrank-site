Who This Plan Suits

This plan fits developers who are comfortable working on a server over SSH and want a small Cloud VPS for a side project, a personal API, a webhook receiver or a staging copy of an app. The listed resources are 1 GiB of RAM and 25 GiB SSD storage. That is a modest footprint, so think about whether your runtime, database and any background workers fit together on one machine.

Because this is a self-managed server, the setup is up to you. You choose and install the web server or app runtime, keep the operating system patched, configure a firewall and decide how backups work. If you would rather not maintain a server, a managed hosting product may suit you better than a VPS.

The plan's features list a "Flat monthly price (no intro discount)", and the term is listed as 1 month. The renewal price is the same as the intro price, so the amount in the price table is what the plan costs per cycle. Check the price table on this page for the current figure.

Some details are not covered here. The official data does not list the plan's CPU allocation, bandwidth allowance, billing method, a backup or snapshot service, or a provider-level firewall. Confirm each of these on DigitalOcean's own pricing and product pages before you sign up, especially bandwidth if your API serves a lot of traffic.

What a Self-Managed Server Needs

SSH access is how you will manage the server, so set up key-based login early and keep your private key safe. Plan who else, if anyone, needs access, and give each person their own key rather than sharing one.

Updates are your responsibility. Turn on automatic security updates for the operating system packages, and keep a habit of updating your app's own dependencies. A small API that sits untouched for months is an easy target if its packages are out of date.

A firewall should allow only the services you actually use, typically SSH, HTTP and HTTPS. Everything else should stay closed, and that includes database services, which should listen only locally unless you have a specific reason to expose them.

Backups need a plan that works even if the server itself is lost. Export your database and archive your files on a schedule, store copies somewhere other than the server, and test a restore at least once so you know the process works.

Practical setup guide

  1. STEP 1Create the server and note its IP address

    Create the DigitalOcean Basic 1 GiB server, add your SSH public key during setup if the option is offered, and write down the server's public IP address. Log in over SSH and confirm you can reach a shell before doing anything else.

  2. STEP 2Lock down SSH, updates and the firewall

    Create a non-root user with sudo rights, confirm key-based login works for it, then disable password login. Enable automatic security updates for the operating system. Configure a firewall that allows only SSH, HTTP and HTTPS.

  3. STEP 3Deploy the app and point DNS at the server

    Install your web server or runtime, deploy the side project or API, and test it directly on the server. Once it responds correctly, add A records, and AAAA records if you use IPv6, at your DNS provider pointing to the server's IP. Replace example.com with your domain and check the result from your own computer: dig +short A example.com

  4. STEP 4Issue a TLS certificate

    After DNS resolves to the new server, install Certbot following its official instructions. If you serve the site through Nginx, replace example.com and www.example.com with your own names and run: sudo certbot --nginx -d example.com -d www.example.com

  5. STEP 5Set up backups and note the billing cycle

    Schedule regular database exports and file archives, copy them to storage outside the server, and test a restore. Note the date your monthly cycle renews. The renewal price is the same as the intro price, as shown in the price table.
