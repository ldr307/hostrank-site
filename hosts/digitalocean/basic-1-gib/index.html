What the official data lists for this plan

The official data for DigitalOcean Basic 1 GiB lists two resources: 1 GiB of RAM and 25 GiB SSD storage. It does not list a CPU count or a bandwidth allowance, and it does not list included backups, snapshots, a firewall service, monitoring, operating system choices or data center locations. A developer who needs any of those figures or features should confirm them with DigitalOcean before paying, because nothing on this page can fill those gaps.

The single feature in the data is written as Flat monthly price (no intro discount). The billing field, however, says the plan is billed per second up to the monthly price, so the monthly figure in the price table is a cap on per-second charges rather than a single fixed amount that appears unchanged on every invoice. The data does not say what, if anything, lowers charges below that cap, so treat the cap as the figure to budget for and ask DigitalOcean how charges behave for a server that is no longer needed.

How per-second billing and the monthly cap work

Charges build up by the second while the server exists, and the official data states that they are capped at 672 hours a month. Once the cap is reached, the amount for that billing cycle is the monthly price in the table and no more. The 1 month term in the data is simply the length of that billing cycle; it is not a period the account is tied to, and there is no separate figure to compare against the first cycle, because the data shows the renewal price is the same as the intro price.

For a side project this matters in a practical way: a server that runs the whole month costs the capped monthly amount, and a server created and destroyed within a shorter window accrues charges for the seconds it existed, as the billing field describes. Anything beyond that, such as how a stopped but not destroyed server is charged, is not covered by the data and should be confirmed with the provider.

Who this plan suits

The plan fits a developer who wants a small Linux server for a hobby API, a webhook receiver, a bot, a staging copy of a larger project or a personal tool, and who is comfortable administering the operating system. With 1 GiB of RAM, the workload should be a lightweight runtime, a small database or a static site rather than a memory-hungry stack; whether that fits depends on the application, and the data gives no benchmark or performance figures to settle it.

It also suits someone who prefers usage-based charging over a fixed up-front period. Because billing is per second up to the monthly price, spinning up a server to test an idea and tearing it down again follows the same billing model as a server that runs all month. A developer who expects to resize later should note that the data for this plan does not list a CPU count or bandwidth, so those two factors cannot be compared here against other plans.

What a self-managed server needs: SSH access, updates, a firewall and backups

A Cloud VPS in this category is self-managed, which means the provider supplies the virtual machine and the account holder is responsible for everything inside it. In practice that starts with SSH access using key authentication rather than a password, followed by applying operating system updates immediately and enabling automatic security updates so patches land without manual logins.

A host firewall comes next. For a small API, the usual rule set allows SSH, HTTP and HTTPS and denies everything else; the firewall should be enabled from a session that is already connected, with a second terminal used to confirm that a fresh SSH login still works before the first session is closed. Services that only the application needs, such as a database, should listen on the local interface or be restricted to the server itself.

Backups are the item developers most often postpone. Since the plan's listed features do not include a backup service, the safe assumption is that the account holder must arrange copies of application data and the database, stored somewhere other than the server's own 25 GiB SSD. A scheduled export of the database plus a copy of the deployment configuration is enough for most side projects, and a restore should be rehearsed once so that it is known to work.

Practical setup guide

  1. STEP 1Create the server and record its IP address

    Create the server in your DigitalOcean account, selecting an SSH key for authentication rather than a password so the first login is already key-based. Choose the operating system image you know how to administer, since the data does not list the available choices. Once the server is running, note its public IP address; the domain records and the firewall test in later steps depend on it.

  2. STEP 2Patch the system and enable a firewall before exposing anything

    Log in over SSH, apply all pending operating system updates, and turn on automatic security updates so future patches install without a manual session. Configure a host firewall that allows SSH, HTTP and HTTPS and denies the rest, then open a second terminal and confirm a new SSH login works before closing the first. Install the reverse proxy, such as Nginx, and deploy the application so it answers over plain HTTP on the server's IP.

  3. STEP 3Point the domain's A and AAAA records at the server

    In your DNS provider, set the domain's A record to the server's public IP and, if the server has an address for it, the AAAA record as well. Do this only after the application responds correctly on the IP, so the switch does not send visitors to an empty server. Verify the live answer with the placeholder replaced by your own domain: dig +short A example.com.

  4. STEP 4Issue the TLS certificate once DNS resolves to the server

    When the DNS check returns the new IP, install Certbot and request a Let's Encrypt certificate for the domain and its www name, replacing the placeholders with your own hostnames: sudo certbot --nginx -d example.com -d www.example.com. Confirm that the site loads over HTTPS and that HTTP requests redirect to HTTPS. Keep the proxy configuration under version control alongside the application so it can be rebuilt on a fresh server.

  5. STEP 5Set up off-server backups and note the billing details

    Schedule exports of the database and copies of the application configuration to a location other than the server's own 25 GiB SSD, and rehearse one restore so the procedure is known to work. Ask DigitalOcean how charges behave for a server that is stopped or no longer needed, since the official data does not describe that.
