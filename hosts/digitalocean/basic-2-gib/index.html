How per-second billing works on this plan

On shared hosting, a monthly plan is usually a single fixed charge. Here the billing field says the plan is billed per second up to the monthly price, capped at 672 hours a month. In practice, charges build up second by second while the server exists, and the monthly price shown in the table is the ceiling those charges can reach within the billing cycle. The 1 month term is the cycle that cap applies to, not a required period of use.

The listed feature, Flat monthly price (no intro discount), tells you that there is no discounted first cycle followed by a higher one, which matches the renewal price being the same as the intro price. It does not mean every month is the same fixed charge regardless of usage; because billing is per second, the monthly figure is the most a full month of usage reaches.

The official data does not say whether a powered-off or deleted server continues to accrue charges, or what action, if any, pauses them. Do not assume that stopping the server lowers the bill; confirm this with the provider before relying on it.

What changes when you leave shared hosting

On shared hosting, the host installs and patches the operating system, web server, PHP and database, and often handles SSL certificates and backups behind a control panel. On a self-managed Cloud VPS like this one, each of those tasks moves to you. Nothing in the official data confirms a WordPress image, a control panel or a one-click installer, so plan to install the web server, PHP and database yourself or with a tool you choose and trust.

The day-to-day vocabulary also changes. Instead of a file manager and a phpMyAdmin icon, you will log in over SSH, run commands, edit configuration files and read logs. WordPress itself works the same way once the stack is running, but the layer underneath it is now yours to understand and maintain.

Budget time for this before the move. A single WordPress site with a handful of plugins is a reasonable first project for self-managed hosting, but the first setup, the first migration and the first time something breaks all take longer than they would with a host that manages the server for you.

Security updates, firewall and backups on a self-managed server

Security updates are the task most people underestimate. On shared hosting they happen without you noticing; on this plan nobody applies them unless you do. Turn on automatic security updates for the operating system as soon as the server is created, and keep WordPress core, themes and plugins updated from the WordPress dashboard or with WP-CLI. Use SSH keys instead of passwords for the server login and enable two-factor authentication on the DigitalOcean account.

A firewall should allow only the services the site needs: SSH for administration and HTTP and HTTPS for visitors. Everything else, including the database, should be closed to the public internet. Review the firewall again after installing any new software.

Backups deserve the most attention, because the official data for this plan does not list any backup or snapshot feature. Plan to make your own: export the WordPress database and archive the site files on a schedule, and copy both somewhere off the server. If WP-CLI is installed, the database can be exported to the home folder, outside the public web folder, with this command, replacing the path if you store backups elsewhere: wp db export ~/backup.sql

A backup you have never restored is only a guess. Practice restoring the database export and the file archive to a test location at least once so that a real failure is a routine task rather than a crisis.

Practical setup guide

  1. STEP 1Create the server and record its IP address

    After signing up, create the server and choose an operating system image; the official data does not say which images are offered, so review the choices before you commit. Note the public IP address the server is given and log in over SSH, using an SSH key rather than a password. Create a non-root user for daily work and give it sudo rights.

  2. STEP 2Install the web stack and move the WordPress site

    Install a web server such as Nginx, PHP and a MySQL-compatible database, then copy the WordPress files and a database export from the shared host to the new server. Import the database, update the WordPress configuration with the new database details, and test the site on the new server before changing any DNS. Do not move traffic until the site loads correctly here.

  3. STEP 3Point the domain's A/AAAA records at the new server

    At the registrar or DNS provider that holds the domain, change the A record (and the AAAA record if the server has an IPv6 address) to the new server's IP address. Keep the shared hosting account active until the change has propagated and the site is confirmed to be served from the new server. Only then cancel the old plan.

  4. STEP 4Issue a TLS certificate once DNS points at the server

    When the domain resolves to the new server, install Certbot and request a Let's Encrypt certificate so the site is served over HTTPS. If the site runs on Nginx, this command issues and installs the certificate, with example.com and www.example.com replaced by your own domain: sudo certbot --nginx -d example.com -d www.example.com. Then open the site in a browser and check that the padlock appears and that plain HTTP redirects to HTTPS.

  5. STEP 5Harden the server, schedule backups and note the billing

    Turn on automatic security updates, set the firewall to allow only SSH, HTTP and HTTPS, and schedule a database export and a file archive that are copied off the server. Keep WordPress core, themes and plugins updated. Billing on this plan builds up per second up to the monthly price, capped at 672 hours a month, with the price staying the same after the first cycle; confirm with the provider how charges behave for a powered-off or deleted server, since the official data does not say.
