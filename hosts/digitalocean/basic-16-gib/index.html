What the official data lists for this plan

The official pricing data lists three resource figures for DigitalOcean Basic 16 GiB: 8 vCPU, 16 GiB of RAM and 320 GiB SSD. For a side project that is a comfortable footprint: a small API, its database, a reverse proxy and a background worker can share the server without competing for memory. The data does not list a bandwidth or transfer allowance for this plan, so confirm that figure on the provider's pricing page before signing up if the project will serve large downloads or media.

The category is Cloud VPS and the plan is a self-managed server. The operating system, the web server, the runtime, security patches, the firewall and backups are all the account holder's responsibility rather than the provider's. The feature list contains a single line, Flat monthly price (no intro discount), and nothing about server locations, operating system choices or included tooling, so anything beyond the resource figures should be checked with the provider.

How per-second billing up to a monthly cap works

Billing is listed as USD per month; billed per second up to the monthly price (capped at 672 hours a month). In practice, charges build up second by second and stop climbing once they reach the monthly price shown in the price table for that month. The term of 1 month is the billing cycle of that cap. The official data does not say what pauses or stops charges, for example whether a powered-off server continues to accrue, so do not assume that and confirm it with the provider.

The feature list names a flat monthly price with no intro discount, and the renewal price is the same as the first-term price, so there is no discount that ends. Because billing is per second, read the monthly price in the table as the ceiling for one month rather than as an identical charge taken every month.

Who DigitalOcean Basic 16 GiB suits

This plan fits a developer whose side project has outgrown a small instance: an API plus a PostgreSQL or MySQL database, a Redis cache, a queue worker and the occasional build or test run all on one machine. With 8 vCPU the server can run several of those at once without a single busy process starving the API, and 16 GiB of RAM leaves headroom for database caches and language runtimes that are memory hungry. The 320 GiB SSD holds code, database files, logs and local backup archives before anything needs to be shipped elsewhere.

It is more than a static site or a tiny webhook endpoint needs. A project at that scale may be better served by DigitalOcean Basic 8 GiB, which is described in the comparison below, with this plan as the step up when memory or CPU runs short. A developer who wants the provider to handle patching and backups should look at managed hosting instead, because none of that is part of a self-managed Cloud VPS.

What a self-managed server needs: SSH, updates, firewall, backups

Access to a Cloud VPS is over SSH. Use an SSH key instead of a password, keep the private key on the developer's own machine, and create a non-root user with sudo for everyday work so the root account is not the one facing login attempts from the internet. Once key login is confirmed, disable password authentication in the SSH daemon configuration.

Apply operating system security updates on a schedule rather than when something breaks. Most Linux distributions offer an unattended security update option; turn it on, and still reboot when a kernel update asks for it. Keep the application runtime, whether Node, Python, Go or something else, updated separately, since distribution packages often lag behind upstream releases.

Run a host firewall on the server that allows SSH, HTTP and HTTPS and denies everything else by default. If the API talks to a database or cache on the same machine, bind those services to localhost so they are never reachable from outside. The official data does not mention a provider-side firewall or any backup or snapshot feature for this plan, so plan on the host firewall as the baseline and treat backups as something to build yourself; check the provider's documentation for anything extra before relying on it.

For backups, export the database to a file on a schedule, archive the application directory, and copy both off the server to object storage or another machine. A copy that lives only on the same disk is not a backup. Restore once onto a fresh server to prove the process works; an untested backup is only a hope.

A developer running a latency-sensitive API who wants to know what the CPU is has more to go on with the Vultr descriptions; a developer who mainly wants more parallel capacity for workers and builds has the 8 vCPU figure on DigitalOcean Basic 16 GiB to compare against the Vultr vCPU counts.

Practical setup guide

  1. STEP 1Create the server and record its IP address

    Create the server with the Linux distribution the project targets, adding the public SSH key during creation if the flow offers it, or placing it in the authorized keys file right after the first login. Note the IPv4 address, and the IPv6 address if one is assigned, from the server details. Log in over SSH, create a non-root user with sudo, and confirm that key-based login for that user works before closing the root session.

  2. STEP 2Patch, firewall and deploy before any traffic arrives

    Update every package, enable automatic security updates, and disable password authentication for SSH. Turn on a host firewall that allows SSH, HTTP and HTTPS and denies everything else, and bind the database or cache to localhost. Install Nginx as a reverse proxy, deploy the API behind it, and test against the raw IP address so problems are found while the domain still points elsewhere.

  3. STEP 3Point the domain at the server

    At the DNS provider, create an A record for the domain with the server's IPv4 address and an AAAA record with the IPv6 address if one is in use. If the site is moving from another host, do this only after the new deployment answers correctly on the IP address. Wait until lookups from your own machine return the new address before continuing.

  4. STEP 4Issue a TLS certificate once DNS resolves

    With the domain resolving to the server, install Certbot and request a Let's Encrypt certificate for Nginx, replacing example.com and www.example.com with your own hostnames: sudo certbot --nginx -d example.com -d www.example.com. Then confirm HTTPS answers and any HTTP redirect behaves, again substituting your own domain: curl -I https://example.com. Fix the Nginx configuration if the headers are not what the API expects.

  5. STEP 5Schedule backups and note the billing

    Set up a scheduled database export and an archive of the application directory, copy both off the server, and run a restore on a fresh server once to prove it works. For billing, remember that charges build up per second up to the monthly price shown in the price table, capped at 672 hours a month, and that the 1 month term is the billing cycle of that cap. The renewal price is the same as the first-term price with no intro discount, so the figure in the table is the monthly ceiling to budget for.

Frequently asked questions

  • Is DigitalOcean Basic 16 GiB billed hourly or monthly?

    The official data lists it as USD per month; billed per second up to the monthly price (capped at 672 hours a month). Charges accumulate per second and cannot exceed the monthly price in the price table for that month. The 1 month term is the billing cycle of that cap.

  • Does the price change after the first month?

    No. The renewal price is the same as the first-term price, and the feature list states Flat monthly price (no intro discount). The monthly figure in the table is a ceiling because billing is per second, not a fixed charge taken every month.

  • How does it differ from DigitalOcean Basic 8 GiB?

    Both have the same billing wording, term and no intro discount. DigitalOcean Basic 16 GiB lists 8 vCPU, 16 GiB of RAM and 320 GiB SSD; DigitalOcean Basic 8 GiB lists 4 vCPU, 8 GiB of RAM and 160 GiB SSD. The smaller plan suits an API and database that stay small; the larger one suits a project that also runs workers, caches or builds on the same server.

  • What should a developer do first after the server is created?

    Log in over SSH with a key, create a non-root sudo user, disable password login, apply all pending security updates and enable automatic security updates, then turn on a host firewall that allows only SSH, HTTP and HTTPS. Only after that should the API be deployed and the domain pointed at the server.

  • Is there a longer term or an annual discount?

    The official data lists only a 1 month term and no intro discount for this plan. Nothing else is listed, so if a different billing cycle matters to you, confirm it with the provider before paying.
