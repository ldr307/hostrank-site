Resources listed for this plan

The pricing page lists this plan as 4 vCPU, 8 GiB of RAM and 160 GiB SSD. These are the figures to size against. Note that the units are given in GiB rather than GB, so when comparing against other providers, only line up figures that use the same unit.

How per-second billing and the monthly cap work

Billing is listed as USD per month; billed per second up to the monthly price (capped at 672 hours a month). In practice, charges accrue second by second while the server exists, and once usage reaches the monthly cap, the price shown in the table is what applies for that cycle. The 1 month term describes the billing cycle for that cap, not a required period.

The features list a flat monthly price (no intro discount), and the renewal price is the same as the intro price, so there is no first-term rate to watch for. Because the plan is billed per second, treat the monthly figure as the ceiling on charges rather than a fixed amount charged every month regardless of usage. The data does not say which actions stop or reduce charges, so confirm that with DigitalOcean rather than assuming.

Matching vCPU, memory and storage to the app

4 vCPU gives a web app room to run several worker processes in parallel. Request-heavy endpoints, background job queues, and build or test steps that run on the same server are the workloads where vCPU count tends to matter most. If the app spends most of its time waiting on a database or an external API, memory usually fills up before CPU does, and the vCPU count becomes less of a constraint.

8 GiB of memory is the figure to check against the combined footprint of the application processes, any database or cache that runs alongside them, and the operating system itself. Running an application server, a relational database and an in-memory cache on one server is a common layout at this size, but the actual headroom depends on how much each of those components keeps in RAM and how many application workers are started.

160 GiB SSD covers the operating system, application code, logs, user uploads and database files. Storage is easy to under-plan on an app that stores uploads or keeps verbose logs, so estimate the growth rate and leave room for local database dumps before they are shipped off the server. Keeping logs rotated and uploads on a separate path makes it easier to see which part of the disk is growing.

Resizing later

The listed data does not mention whether this plan can be resized up or down, or whether moving to a different size means creating a new server and migrating the app. Before choosing a smaller size with the intention of growing into a larger one, confirm with DigitalOcean how resizing works, whether storage can be changed independently of CPU and memory, and whether a resize involves downtime.

A practical fallback that does not depend on provider features is to start on the size that fits current load with some headroom and keep deployment scripted, so that moving to a larger server is a repeatable process rather than a manual rebuild. Measuring memory and CPU use after launch gives a clearer signal for when to move than guessing at signup.

Who this plan suits and what to check before signing up

This plan suits a developer running a web app that needs more memory or more parallel capacity than a 2 vCPU, 4 GiB server, and who is comfortable administering the operating system, web server, updates and backups directly. As a self-managed server, the application stack, TLS certificates and firewall are set up and maintained by the user rather than by the provider.

Before signing up, read the price table for the monthly cap, keep in mind that the plan is billed per second up to that cap with a 1 month billing cycle and the same price thereafter, and resolve the two open points covered above, transfer allowance and resizing, with DigitalOcean. If the app depends on a specific operating system, runtime version or region, confirm those with the provider as well, since the listed data covers only resources and billing.

Practical setup guide

  1. STEP 1Create the server and record its IP address

    Create a DigitalOcean Basic 8 GiB server with the operating system image that the app's dependencies target. Once it is running, note its public IPv4 address and, if one is assigned, its IPv6 address, then connect over SSH as the initial user to confirm access. Keep in mind that per-second charges begin accruing toward the monthly cap from this point.

  2. STEP 2Deploy the app, then point the domain at the server

    Install the web server, runtime and database, deploy the app, and test it against the server's IP address or a temporary hostname before moving any live traffic. When the app responds correctly, create or update the domain's A record (and AAAA record if using IPv6) at the DNS provider so it points at the new IP. Confirm the change has propagated, replacing example.com with the actual domain: dig +short A example.com

  3. STEP 3Issue a TLS certificate once DNS resolves

    After the A/AAAA records resolve to the new server, request a certificate so the app is served over HTTPS. If the site runs behind Nginx, this command issues and installs a Let's Encrypt certificate; replace example.com and www.example.com with the real hostnames: sudo certbot --nginx -d example.com -d www.example.com Then load the site in a browser and check that HTTP requests redirect to HTTPS.

  4. STEP 4Set up security updates, a firewall and backups

    Enable automatic security updates for the operating system and configure a host firewall that allows SSH, HTTP and HTTPS and denies everything else by default. The listed data does not confirm a provider backup or snapshot service for this plan, so check what DigitalOcean offers and, in any case, schedule database dumps and file archives that are copied off the server. Finally, note the monthly cap from the price table and remember that charges accrue per second up to that figure; confirm with DigitalOcean how destroying or changing the server affects billing.
