What the official data lists for this plan

The plan page lists four resources: 2 vCPU, 2 GB of RAM, 80 GB NVMe SSD storage and 3 TB of bandwidth. The two listed features are High Frequency (3GHz+ Intel Xeon, NVMe SSD) and flat monthly price (no intro discount). The term is 1 month, and billing is described as USD per month; billed hourly up to the monthly price.

That is the full extent of what the official data states. It does not mention server locations, operating system images, IPv6, snapshots, a firewall feature, backups or support channels, so none of those are claimed on this page. The sections below point out where that matters for a developer who intends to run a side project or a small API on this server.

How hourly billing up to a monthly price works

Charges on this plan build up by the hour, and the total for a billing cycle is capped at the monthly price shown in the price table. The 1 month term is the length of that billing cycle, which is the period over which the hourly charges accumulate before the cap applies. The feature list calls the price flat with no intro discount, and the official data lists the renewal price as the same as the first-term price, so there is no introductory rate that later gives way to a different one.

Because the feature list says flat monthly price while billing says billed hourly up to the monthly price, the accurate way to read it is that the monthly price is a ceiling rather than a fixed charge that is identical in every cycle. The official data does not say what happens to charges when a server is powered off, idle or deleted part way through a cycle, so do not assume that stopping a server reduces the amount billed. Confirm those details in Vultr's billing documentation before you create anything you may later want to pause.

Who this plan suits

A developer with a side project or a small API is working with a modest, predictable footprint: a web server or reverse proxy, an application runtime, perhaps a small database and a handful of background jobs. On paper, 2 vCPU and 2 GB of RAM is a common starting size for that kind of workload, and 80 GB NVMe SSD leaves room for logs, a database and local backup archives before you need to think about external storage. The 3 TB bandwidth allowance is listed as part of the plan rather than as a separate meter.

The High Frequency (3GHz+ Intel Xeon, NVMe SSD) label is Vultr's own description of the hardware class. The official data does not include benchmark figures, request rates or latency numbers, so treat the label as a hardware description rather than a measured result for your particular application. If your API does CPU-bound work per request, you may want to run your own load test on an hourly-billed server before committing to a full cycle.

This plan is less of a fit if you want a provider to handle patching, monitoring and restores for you. It is a self-managed server, which means everything above the hypervisor is your responsibility. The next section lays out what that involves.

What a self-managed server needs: SSH, updates, a firewall and backups

As a self-managed Cloud VPS, this plan gives you a server that you log into over SSH with root or sudo rights and configure yourself. The first thing to do after creating it is to log in with an SSH key, disable password logins for SSH, and create a non-root user for day-to-day work. Keep your private key out of the server and treat the root account as something you rarely use directly.

Updates are on you. Plan to apply security updates for the operating system on a schedule, and decide early whether you want unattended security updates or a manual routine tied to your deployment process. For an API that ships often, pinning your runtime and library versions in the project and letting the operating system handle its own security patches is a workable split.

A firewall should be in place before the application is reachable. Allow SSH, HTTP and HTTPS and deny everything else by default, and open additional services only when a specific component needs them. If your database only talks to the application on the same machine, bind it to the local interface so it is never exposed. The official data does not confirm whether Vultr includes a network-level firewall, snapshots, automatic backups, a specific set of operating system images, IPv6 addressing or particular server locations with this plan, so check each of those on the provider's site before signing up if any of them matters to your setup.

Backups are the part most side projects skip until something breaks. At a minimum, export the database on a schedule and copy both the export and your application configuration to a location that is not this server. Test a restore once on a fresh server so you know the procedure works and how long it takes. Because charges are hourly, creating a short-lived server to rehearse a restore is a reasonable way to validate your backups.

Practical setup guide

  1. STEP 1Create the server and note its IP address

    Create the High Frequency server from your Vultr account, choosing an operating system image you are comfortable administering and adding your public SSH key during creation. Once it is running, note the IP address shown for the server. Log in over SSH, create a non-root user with sudo rights, and disable password logins for SSH.

  2. STEP 2Point the domain's A/AAAA records at the server

    In your DNS provider, add an A record for your domain pointing at the server's IP address, plus an AAAA record if the server has an IPv6 address assigned. Do this only once the server exists, and do not move production traffic until the application is installed and responding. You can confirm what the domain currently resolves to from your own machine, replacing the placeholder with your domain: dig +short A example.com

  3. STEP 3Issue a TLS certificate once DNS points at the server

    Install your web server or reverse proxy and get the application responding over plain HTTP first. After the domain resolves to the new server, install Certbot and request a Let's Encrypt certificate, replacing both hostnames with your own: sudo certbot --nginx -d example.com -d www.example.com. Then confirm the site loads over HTTPS in a browser and that HTTP redirects to it.

  4. STEP 4Lock down the server with updates and a firewall

    Apply all pending operating system updates and decide whether security updates will install automatically or on a schedule you run. Enable a host firewall that allows SSH, HTTP and HTTPS and denies everything else by default. Bind the database and any internal services to the local interface so they are not reachable from the public network.

  5. STEP 5Set up backups and understand the billing cycle

    Schedule a database export and a copy of your application configuration to a location outside this server, and run a restore once on a fresh server to prove the procedure works. The official data does not confirm provider-side backups or snapshots, so treat your own backups as the primary copy until you have checked. Remember that charges build up by the hour up to the monthly price in the price table over each 1 month cycle, and confirm with Vultr how charges behave for a server you power off or delete.
