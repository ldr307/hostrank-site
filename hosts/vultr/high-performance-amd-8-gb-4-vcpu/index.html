What the official data lists for this plan

The plan is listed as 4 vCPU, 8 GB of memory, 180 GB NVMe SSD and 6 TB of bandwidth. The feature line reads High Performance (AMD EPYC, NVMe SSD), which places it on Vultr's AMD-based hardware line with NVMe storage rather than the regular SSD line. The second feature line, flat monthly price (no intro discount), tells you the headline figure in the table is not a promotional rate that later changes.

This is a self-managed Cloud VPS. Vultr provides the virtual machine; the operating system, web server, runtime, database and everything else on it are installed, configured and maintained by you. That is the normal arrangement for a developer who wants to run a specific stack, but it also means there is no managed layer handling updates or application tuning on your behalf.

How hourly billing up to the monthly price works

The billing field reads USD per month; billed hourly up to the monthly price. In practice, charges build up by the hour for as long as the server exists, and they stop increasing once they reach the monthly price shown in the table. The listed 1 month figure is the cycle of that monthly cap, not a period you sign up for in advance.

Because renewal_vs_intro is listed as same, the renewal price equals the intro price: the monthly cap you see for the first cycle is the cap for later cycles as well, with no intro discount that ends. Although the features describe a flat monthly price, the hourly billing field is the one that governs how you are charged, so treat the monthly price as a ceiling rather than as an identical charge every month regardless of how long the server existed.

The official data does not say whether a server that is powered off, stopped or deleted continues to accrue charges, or at what point charges end. If you plan to spin servers up and down while testing sizes, confirm Vultr's rules on that point before relying on them.

Matching 4 vCPU and 8 GB to the app

Memory is usually the first number to size for a web app, because it sets how many application workers, how large a database buffer pool and how much cache you can run on one machine without swapping. With 8 GB, you have room to run an application server and a database on the same host, but the right split depends on the app's measured footprint under load rather than on any general rule. Profile the app on a staging box and note peak resident memory per worker before deciding.

The 4 vCPU figure matters most for CPU-bound work: request rendering, template compilation, image processing, background jobs and build steps. If your app spends most of its time waiting on the database or on external APIs, extra vCPU does less for you than extra memory would. The official data does not state how the 4 vCPU map to physical cores or which AMD EPYC generation is used; the only hardware description given is High Performance (AMD EPYC, NVMe SSD).

Storage and transfer: 180 GB NVMe SSD and 6 TB

The 180 GB NVMe SSD holds the operating system, the application, the database, logs and any local copies of backups, so budget for all of them rather than just the code. Databases and log directories tend to be the parts that grow unexpectedly, so monitor disk usage from the start. NVMe storage is called out in the feature wording, which is relevant if your database does a lot of random reads and writes.

Bandwidth is listed as 6 TB. For a web app, estimate transfer from average response size multiplied by expected requests, plus any file uploads, downloads or API traffic the app serves. The official data does not describe what happens if transfer exceeds 6 TB in a cycle, so check Vultr's overage rules if the app serves large files or media.

Resizing later

The official data does not confirm whether this plan can be resized in place, whether storage can be expanded separately, or how a change of plan affects charges within a cycle. If the ability to move between sizes without rebuilding matters to you, verify it with Vultr before you deploy.

A practical way to stay flexible regardless of the answer is to make the server easy to recreate: keep configuration in environment variables or a provisioning script, take regular database dumps, and store application files in version control. The three Vultr alternatives in this data carry the same billing field, billed hourly up to the monthly price, so a replacement server on a different size is charged in the same hourly way while you migrate.

Practical setup guide

  1. STEP 1Create the server and record its IP address

    Deploy the Vultr High Performance AMD 8 GB / 4 vCPU server with the operating system image your stack needs and note the public IP address assigned to it. Connect over SSH, apply the available package updates, and install your web server, runtime and database. Deploy the app and confirm it responds on the server's IP address before any public traffic is sent to it.

  2. STEP 2Point the domain's A and AAAA records at the server

    In your DNS provider, set the domain's A record to the server's IP address, and add an AAAA record only if the server has an IPv6 address. Check what the domain currently resolves to from your own machine, replacing example.com with your domain: dig +short A example.com. Do not move on to certificates until that command returns the new server's address, because validation depends on the domain reaching this server.

  3. STEP 3Issue a TLS certificate once DNS resolves to the server

    Install Certbot following the Certbot project's instructions for your operating system. If the app sits behind Nginx, request and install a Let's Encrypt certificate, replacing both hostnames with your own: sudo certbot --nginx -d example.com -d www.example.com. Afterward, load the site over HTTPS in a browser and confirm that plain HTTP redirects correctly.

  4. STEP 4Set up security updates, a firewall and backups

    Enable automatic security updates for the operating system so patches are not left to memory. The official data does not confirm a provider firewall, snapshots or a backup feature for this plan, so configure a host firewall that allows only SSH, HTTP and HTTPS, and schedule database dumps and file archives that are copied off the server. Ask Vultr whether snapshot or backup options exist before relying on anything beyond your own copies.
