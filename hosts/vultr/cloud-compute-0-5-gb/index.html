Who this plan suits

The plan fits agencies that want one isolated server per project instead of many sites sharing one machine. Separate servers make it easier to hand a client their own environment, revoke a contractor's access without touching other projects, and see costs per client.

With 1 vCPU and 0.5 GB of RAM, this is the entry size in the Vultr Cloud Compute line compared on this page. Whether that is enough for a given staging site, CMS or client workload is not confirmed in the data, so agencies should judge it against their own stack. Projects that need more memory or storage can look at the larger plans in the comparison below.

Because this is a self-managed server, the agency handles the operating system, web server, security updates, firewall and backups. That suits teams with in-house server skills or a standard build process they repeat for every client.

Keeping access organized per client

Give every client server its own SSH keys for the people who need them, and remove keys when a team member or freelancer leaves the project. Keep a simple record per client listing the server, its IP address, the domains pointed at it and who holds access.

Before handing a site over or switching DNS, confirm where the domain points with this command, replacing example.com with the client's domain: dig +short A example.com

Practical setup guide

  1. STEP 1Create the server and record it per client

    Create the server and note its IP address. Label it with the client or project name so it is easy to match with invoices and access records. Add only the SSH keys of the people working on that project.

  2. STEP 2Secure the server before deploying

    Install security updates and set up automatic updates for the operating system. Configure a firewall that allows only SSH, HTTP and HTTPS. Keep a list of who has SSH access for this client.

  3. STEP 3Deploy the site, then point DNS

    Install your web server and deploy the staging or client site, then test it using the server's IP address. Once the site is ready, point the domain's A record, and AAAA record if you use IPv6, at the server's IP. Do not move traffic until the new site works.

  4. STEP 4Issue a TLS certificate

    After DNS points at the new server, issue a certificate. If you use Nginx with Certbot installed, run this command after replacing example.com with the client's domain: sudo certbot --nginx -d example.com -d www.example.com

  5. STEP 5Set up backups and note billing details

    Backups are not confirmed in this plan's features, so check with Vultr and set up your own backups of site files and databases, stored off the server. Record the server's term of 1 month and its price from the table in your client billing notes.
