What the plan includes

The official pricing page lists four resources for this plan: 1 vCPU, 2 GB of memory, 55 GB SSD storage and 2 TB of bandwidth. For a developer this translates into a single core for a runtime such as Node, Python or Go plus a reverse proxy, enough memory for a small service and possibly a lightweight database, local SSD space for code, logs and a database file, and a monthly transfer allowance that a low-traffic API or side project is unlikely to approach.

Two feature lines describe the plan. The first is Regular Performance (previous-gen Intel, regular SSD), which is Vultr's own label for this hardware tier; the official data gives no benchmark, clock speed or disk throughput figures for it, so treat the label as a tier name rather than a performance promise. The second is flat monthly price (no intro discount), meaning the listed price is not a promotional first-term rate. How that price is actually charged is explained in the billing section below, because the billing wording matters more than the word flat.

How billing works

Vultr lists the plan in USD per month; billed hourly up to the monthly price. In practice, charges build up hour by hour while the server exists in your account, and they stop climbing once they reach the monthly price shown in the price table. The 1 month figure is the billing cycle of that monthly cap, not a required length of service, so the listed price is a ceiling for the cycle rather than the same fixed charge every month.

The renewal price is the same as the first-term price, which lines up with the flat monthly price (no intro discount) feature: there is no promotional rate that ends after the first cycle. The official data does not say what happens to charges when a server is powered off or destroyed, so check Vultr's billing documentation on that point before assuming anything about stopping or pausing the meter.

Who this plan suits

The plan fits a developer who is comfortable administering a Linux server and wants a small, predictable environment for a side project, a staging copy of an app or a small API that serves a handful of clients. With 1 vCPU and 2 GB of memory, a typical layout is one application process behind Nginx, a small database such as SQLite or a modest PostgreSQL instance, and a cron job or two. Whether that is enough depends on your stack and traffic; the official data contains no load or request-rate figures, so size by measuring your own app.

The hourly billing also suits short-lived use. A developer who spins up a server to test a deployment, reproduce a bug or run a demo for a few days accumulates charges only for the hours the server exists in the account, up to the monthly cap. Someone who needs newer CPUs or NVMe storage for a database-heavy workload should read the comparison section, since Vultr lists other tiers with the same memory.

What a self-managed server needs: SSH, updates, a firewall and backups

As a self-managed Cloud VPS, this plan gives you a server and leaves the operating system to you. You administer it over SSH, so the first job after creation is to log in, add your public key, disable password authentication and create a non-root user with sudo. Everything that a managed host would handle for you, from kernel patches to web server configuration, is your responsibility here.

Updates come next: configure unattended security updates for your distribution and plan a reboot window for kernel changes. A host firewall such as ufw or nftables should allow only SSH, HTTP and HTTPS inbound and drop everything else; if your API listens on an internal port for a local reverse proxy, keep that port closed to the outside. Backups mean an off-server copy of your database dump and application files on a schedule, plus a tested restore, because a single disk on a single server is not a backup.

The official data for this plan does not list a backup or snapshot service, a provider-side firewall, the operating system images offered, server locations, IPv6 availability or support terms. None of these appear in the two feature lines, so confirm each with Vultr before signing up rather than assuming it is included.

DigitalOcean publishes its sizes in GiB while Vultr uses GB and TB, so the figures are not directly comparable on this page; read each provider's own page rather than assuming one is larger.

Within Vultr, High Frequency 2 GB keeps 1 vCPU, 2 GB of memory and 2 TB of bandwidth but is labeled High Frequency (3GHz+ Intel Xeon, NVMe SSD) and lists 64 GB NVMe SSD. High Performance AMD 2 GB is labeled High Performance (AMD EPYC, NVMe SSD) and lists 1 vCPU, 2 GB of memory, 50 GB NVMe SSD and 3 TB of bandwidth. All three Vultr plans share the same billing wording, the same 1 month cycle, the flat monthly price (no intro discount) feature and the same renewal price as the first term.

Which option fits depends on the workload. Cloud Compute 2 GB is the Regular Performance tier, which suits a low-traffic API or side project where the hardware generation matters less than the cap in the price table. The High Frequency tier is the one to look at when NVMe storage and the 64 GB figure matter, for example a larger database file. The High Performance AMD tier lists 3 TB of bandwidth against 2 TB here, which matters for a service that pushes a lot of data. The DigitalOcean plans are the ones to compare when per-second billing or an existing DigitalOcean account is the deciding factor.

Practical setup guide

  1. STEP 1Create the server and record its IP address

    Create the Vultr Cloud Compute 2 GB server from your Vultr account, choosing the operating system image offered during creation and adding your SSH public key at that stage if the creation flow allows it. Note the public IP address assigned to the server; your DNS records and firewall rules will reference it. Log in over SSH as soon as the server is reachable and confirm the key-based login works before changing anything else.

  2. STEP 2Harden the server before it serves traffic

    Create a non-root user with sudo, disable password authentication for SSH, and enable unattended security updates for your distribution. Configure a host firewall such as ufw or nftables to allow only SSH, HTTP and HTTPS inbound, keeping any internal application port closed to the outside. Deploy your application behind Nginx as a reverse proxy and set up a scheduled database dump and file copy to storage outside this server, then run a restore once to prove it works.

  3. STEP 3Point the domain at the server

    Once the app responds on the server's IP address, create an A record for your domain pointing at that IP, and an AAAA record as well if you also use IPv6. Wait until the record resolves from outside before moving on, because the certificate step depends on it. Check what the domain resolves to from your own machine, replacing example.com with your domain: dig +short A example.com

  4. STEP 4Issue a TLS certificate

    With DNS resolving to the server and Nginx serving the site over HTTP, install Certbot following the Certbot instructions for your distribution. Then request and install a Let's Encrypt certificate for the domain and its www name, replacing both placeholders with your own hostnames: sudo certbot --nginx -d example.com -d www.example.com

  5. STEP 5Note how charges accrue

    This plan is charged in USD per month; billed hourly up to the monthly price, so the figure in the price table is the ceiling for each 1 month billing cycle rather than a fixed charge on a set day. The renewal price is the same as the first-term price, so budget on the table figure going forward. Keep an eye on the usage shown in your Vultr account during the first cycle to see how your actual hours line up with that cap.
