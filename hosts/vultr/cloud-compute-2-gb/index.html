Who this plan suits

The plan fits a developer who wants a small server for a side project, a hobby app or a lightweight API and is comfortable working over SSH. With 1 vCPU and 2 GB of RAM, it gives room for a single application, a reverse proxy such as Nginx, and a small database on the same machine.

It suits people who want full control of the stack instead of a managed control panel. The trade-off is responsibility: patching, hardening and backups are tasks for the server owner, not something this page can confirm the provider handles.

Resources as listed

The official pricing page lists these resources: 1 vCPU, 2 GB of RAM, 55 GB SSD storage and 2 TB of bandwidth. The hardware is described as Regular Performance (previous-gen Intel, regular SSD).

The data does not include speed figures or benchmarks, so plan capacity around your own workload. A small API with modest traffic and a compact database is the kind of use these numbers point toward, but load testing your own app is the reliable way to know whether it fits.

How billing works

Billing is listed as USD per month; billed hourly up to the monthly price. In practice, charges build up by the hour, and the monthly price shown in the price table is the cap for the billing cycle, which the data lists as 1 month.

The features describe a flat monthly price (no intro discount), and the price does not differ between a first period and later periods. Since billing is hourly, treat that monthly price as the upper limit rather than as an identical charge every month. Check the price table for the current amount.

What a self-managed server needs

SSH access: you log in to the server yourself to install software and deploy code. Using SSH keys instead of passwords and disabling direct password logins are common first hardening steps.

Updates: keep the operating system and installed packages patched. Enabling automatic security updates through your distribution's package tools reduces the chance of running known-vulnerable software on a public API.

Firewall: allow only the services you need, typically SSH, HTTP and HTTPS, and block the rest. A host-level firewall on the server works regardless of what the provider offers.

Backups: the official data does not confirm a backup or snapshot service, a provider firewall, server locations or available operating system images, so check those on Vultr's site before signing up. Plan your own off-server copies of the database and site files either way.

Practical setup guide

  1. STEP 1Create the server and note its IP

    Create the server with the operating system you plan to use and write down its public IP address. Log in over SSH and set up key-based authentication for a regular user. Disable password logins once key access works.

  2. STEP 2Patch the system and enable a firewall

    Install all pending package updates and turn on automatic security updates. Configure a host firewall that allows only SSH, HTTP and HTTPS. Confirm you can still connect over SSH before closing your session.

  3. STEP 3Deploy and test the app before moving traffic

    Install your runtime, database and a reverse proxy such as Nginx, then deploy your API or site. Test it using the server IP so nothing changes for users yet. Set up a regular off-server copy of your database and files at this point.

  4. STEP 4Point the domain at the server

    At your DNS provider, set the A record to the server IP, and an AAAA record if you use IPv6. Check what the domain resolves to with this command, replacing example.com with your domain: dig +short A example.com

  5. STEP 5Issue a TLS certificate

    Once the domain resolves to the new server, issue a certificate. If you use Nginx with Certbot installed, replace both example.com names with your own domain and run: sudo certbot --nginx -d example.com -d www.example.com
