What the official data shows about this plan

The plan is listed under the Cloud VPS category with the following resources from the official pricing page: 1 vCPU, 2 GB RAM, 55 GB SSD storage and 2 TB bandwidth. Vultr describes the hardware tier as Regular Performance (previous-gen Intel, regular SSD), which sets it apart from the NVMe-based tiers covered in the comparison section below.

The second listed feature is a flat monthly price (no intro discount). In practice this means the monthly figure in the price table is the same figure in later billing cycles, and there is no promotional first-term rate that later changes. Because the billing field says the plan is billed hourly up to the monthly price, that monthly figure works as a cap on what a full billing cycle can cost rather than a single fixed charge; see the billing section for details.

How hourly billing up to the monthly price works

The billing field reads: USD per month; billed hourly up to the monthly price. Charges accumulate by the hour while the server exists, and once they reach the monthly price for the cycle they stop climbing for that cycle. The term listed as 1 month describes the billing cycle of that monthly cap; it is simply the window over which hourly charges are counted against the cap.

The official data does not say what stops, pauses or lowers charges, so do not assume that powering a server off reduces the bill. If your side project or API only needs to run part of the time and you are hoping to pay less than the monthly cap, confirm with Vultr exactly which actions end hourly charges before you rely on that behavior.

Since renewal_vs_intro is listed as the same, the amount you see in the table is the amount that applies in every billing cycle. There is no separate introductory figure to compare against, which keeps cost planning for a long-running project straightforward.

Who this plan suits

A developer hosting a side project, a small REST or GraphQL API, a bot, a webhook receiver or a staging environment is the kind of reader this plan is aimed at. With 1 vCPU and 2 GB of RAM, it has room for a lightweight runtime such as a Node, Python or Go service alongside a reverse proxy and a small database, as long as you keep an eye on memory. The 55 GB SSD is enough for application code, logs and a modest database, and 2 TB of bandwidth covers a large volume of API traffic for a project at this scale.

The Regular Performance tier uses previous-gen Intel CPUs and regular SSD storage, according to the feature wording. If your workload is latency-sensitive or disk-heavy, read the comparison section, where Vultr lists NVMe-based tiers at the same 2 GB RAM size. For a typical side project where cost predictability and a simple hourly model matter more than raw throughput, this plan fits well.

Because this is a self-managed server, you are responsible for the operating system, security patches, the firewall, the web server, TLS certificates and backups. If you would rather not handle those tasks, a managed hosting product is a better match than any plan in this category.

What a self-managed server needs: SSH, updates, firewall and backups

SSH is how you will do everything on a self-managed cloud server. Use key-based authentication from the start, disable password login once your key works, and create a non-root user with sudo rights for day-to-day work. Keep your private key off shared machines and consider a separate deploy key for any CI pipeline that pushes code to the server.

Updates are your job. Enable automatic security updates for the operating system you choose, and schedule a regular check for packages that need a manual restart. For a small API, pin your runtime version in your deployment scripts so an OS update does not silently change the interpreter or runtime your service depends on.

A host firewall should allow SSH, HTTP and HTTPS and deny everything else by default. If your database or cache only needs to be reached by processes on the same server, bind it to the loopback interface and keep it out of the firewall allow list entirely. Review the rules again whenever you add a new service.

Backups need to be designed before you need them. Decide what must survive a loss of the server (usually the database and any uploaded files), export it on a schedule to a location outside the server, and test a restore at least once so you know the procedure works. Infrastructure-as-code or a documented rebuild script is a useful complement, because a 1 vCPU server can be recreated quickly if you can reproduce its configuration.

Practical setup guide

  1. STEP 1Create the server and record its IP address

    Sign up, choose the Cloud Compute 2 GB plan and the operating system image you want, and add your public SSH key during creation. Once the server is running, note its public IP address and connect over SSH with your key. Create a non-root user with sudo rights, confirm that user can log in with the key, and then disable password authentication for SSH.

  2. STEP 2Apply updates and configure the firewall

    Run the package manager's update and upgrade routine and enable automatic security updates for your distribution. Configure a host firewall that allows SSH, HTTP and HTTPS and denies everything else by default. If your database or cache only serves local processes, bind it to the loopback interface so it is never exposed.

  3. STEP 3Deploy the application and point DNS at the server

    Install your runtime and reverse proxy, deploy the API or site, and confirm it responds on the server's IP address over plain HTTP before touching DNS. Then create or update the A record (and the AAAA record if the server has one) for your domain so it points at the new IP. From your own machine you can check what the domain currently resolves to with: dig +short A example.com. Replace example.com with your own domain and wait until the answer matches the server's address.

  4. STEP 4Issue a TLS certificate once DNS resolves to the server

    After the domain points at the server, install Certbot and request a Let's Encrypt certificate. If you are using Nginx as the reverse proxy, the command is: sudo certbot --nginx -d example.com -d www.example.com. Replace both hostnames with your own, then load the site over HTTPS and confirm plain HTTP redirects correctly.

  5. STEP 5Set up backups and review billing details

    Schedule a regular export of your database and any uploaded files to a location outside the server, and run a test restore so the procedure is proven. Keep a script or notes that can rebuild the server's configuration from scratch. Finally, review the price table for the monthly cap, remember that charges accrue hourly up to it, and confirm with Vultr which actions end hourly charges.
