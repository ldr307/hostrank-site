Who this plan suits

The plan is aimed at engineers who want a Cloud VPS with a flat monthly price (no intro discount) instead of a bill that moves with usage. If budgeting and cost forecasting are your main reasons for leaving a usage-billed setup, that billing model is the core point the official data supports.

The listed hardware tier is "Regular Performance (previous-gen Intel, regular SSD)". That wording describes the hardware generation and storage type; it does not include benchmark figures, so measure your own workload after provisioning rather than assuming parity with your current instance.

The term is 1 month, which suits a staged migration: you can run the new server alongside the old one during testing without committing to a long contract.

What the official data does not confirm

The official data does not list data center locations, bandwidth or transfer allowances, backup or snapshot options, firewall features, managed SSL, uptime commitments, or support channels. It also does not explicitly mention SSH or root access in the features. If any of these matter to your service, check them on the provider's own pages before signing up.

Because transfer allowances are not listed, do not assume that every cost is covered by the flat monthly price. If your current bill is driven by egress, confirm how outbound traffic is handled before you treat the move as fully predictable.

Planning a low-downtime cutover

A common approach is to build the new server fully, sync data, lower the DNS TTL on your current records well ahead of the move, then switch DNS once the new server passes your checks. Keeping the old usage-billed server running until traffic has moved reduces the risk of an outage.

For database-backed services, plan a short write freeze or a final sync right before the DNS switch so no writes land on the old server after the copy. Keep the old instance available for rollback until you have confirmed the new one is serving correctly, then shut it down to stop usage charges.

Practical setup guide

  1. STEP 1Build and test before touching DNS

    Provision the server, deploy your application, and run your usual health checks and a load test while production still runs on the old usage-billed server. Lower the TTL on your current DNS records early so the later switch propagates quickly. Keep the old server untouched as a rollback target.

  2. STEP 2Connect the domain

    Point your domain to the new server by updating the A record at your DNS provider, or by changing nameservers if you are moving DNS as well. Once the change is live, confirm which IP address the domain resolves to with this command, replacing example.com with your own domain: dig +short A example.com

  3. STEP 3Enable an SSL certificate

    The official data does not confirm whether an SSL certificate is included, so check the provider's documentation and set up a certificate on the new server before switching traffic. After it is installed, confirm that HTTPS responds and that redirects behave as expected with this command, replacing example.com with your own domain: curl -I https://example.com

  4. STEP 4Confirm how backups and restores work

    The official data does not confirm any backup or snapshot feature for this plan. Find out what options the provider offers, set up your own off-server backups of files and databases if needed, and test a restore before you decommission the old server.

  5. STEP 5Record the renewal date and price

    Note the date of the next charge based on the monthly term and write down the renewal price shown in the table on this page. Once traffic has fully moved and the rollback window has passed, shut down the old usage-billed server so it stops accruing charges.
