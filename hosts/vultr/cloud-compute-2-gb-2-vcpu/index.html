What the official data lists for this plan

The plan comes with 2 vCPU, 2 GB of RAM, 65 GB SSD storage and 3 TB of bandwidth. The pricing page places it in the Regular Performance line, described as previous-gen Intel, regular SSD. The other feature listed is a flat monthly price (no intro discount).

Billing is listed as USD per month; billed hourly up to the monthly price. The billing cycle for that monthly cap is 1 month. Because the data marks the renewal price as the same as the initial price, there is no intro discount that ends later; the amount in the price table is the monthly cap from the start.

Who this plan suits

For an agency, a self-managed server in this size range is a common choice for a staging environment or a single client site that needs its own isolated server rather than a shared account. Having 2 vCPU and 2 GB of RAM on a separate instance means one client's build process or plugin update does not compete with another client's production site, which keeps troubleshooting simpler when a ticket comes in.

The hourly model matters for agency workflows: charges build up by the hour up to the monthly price in the table, so a staging server that only exists for part of a month accrues hourly charges up to that cap. The official data does not say what stops, pauses or lowers charges for a server that is stopped or deleted, so confirm that behavior with Vultr before planning short-lived staging servers around it.

The Regular Performance (previous-gen Intel, regular SSD) description suits projects where consistent resources matter more than peak single-core speed, such as a staging copy, a brochure site, or an internal tool. Projects that lean on database-heavy or disk-heavy work may want to compare the NVMe SSD options covered later on this page.

How billing works per client project

The pricing page states USD per month; billed hourly up to the monthly price. In practice that means each server accrues hourly charges, and those charges stop increasing once they reach the monthly price for that server within the 1 month billing cycle. If each client runs on its own server, each server has its own monthly cap, which makes it straightforward to map a cost to a client.

Because the feature list says flat monthly price (no intro discount) and the renewal price is the same as the initial price, the figure an agency quotes to a client does not depend on whether the server is in its first month or a later one. The official data does not mention cost tags, project labels, sub-accounts or invoices split by server, so an agency that needs billing grouped by client should confirm how invoices are presented before moving multiple clients onto the account.

Keeping access and backups organized per client

As a self-managed server, this plan leaves the operating system, web server, updates and access control to the agency. A practical pattern is one server per client project, with a dedicated SSH key pair per project stored in the agency's secrets manager, and a separate deploy user on each server. That way offboarding a contractor or handing a server to a client means rotating one key, not touching every server.

The official data does not confirm whether snapshots, automatic backups, a firewall or team user management are included with this plan, so plan for backups as part of the server itself: a scheduled database export and a file archive written to a location outside the public web folder, then copied off the server to storage the agency controls. Confirm with Vultr which of these account-level tools exist and whether they add to the hourly charges before signing up.

The listed 65 GB SSD is shared between the operating system, site files, local backups and logs, so a per-client retention policy for on-server backups keeps the disk from filling. The 3 TB of bandwidth applies to this server, which is relevant when a staging server is also used to pull large media libraries from a client's existing host.

Practical setup guide

  1. STEP 1Create the server and record its details in the project file

    After signing up, create the server for the client project, choose an operating system image from whatever Vultr offers at the time, and add the project's dedicated SSH public key when creating it. Note the server's public IP address, the client name and the monthly cap from the price table in the agency's project record so the server can always be matched to a client.

  2. STEP 2Harden the server before anything else lives on it

    Log in over SSH, apply pending security updates and enable automatic security updates for the operating system. Set up a host firewall that allows SSH, HTTP and HTTPS only, disable password logins for SSH, and create a separate deploy user for the project. The official data does not mention a provider-side firewall, so the host firewall is the one to rely on until that is confirmed.

  3. STEP 3Install the stack and stage the site before touching DNS

    Install the web server, PHP and the database, then deploy the client's site files and database to the new server. Test it with a hosts-file override or a temporary subdomain so the client can review it while the live site still runs on the old host. Only move DNS once the staged copy behaves correctly.

  4. STEP 4Point the domain's A/AAAA records at the new server and issue a TLS certificate

    Update the domain's A and AAAA records at the DNS provider to the new server's IP address, replacing example.com with the client's domain when checking propagation from a local machine: dig +short A example.com. Once the records resolve to the new server, issue a Let's Encrypt certificate on the server, again replacing the domain placeholders with the client's domain: sudo certbot --nginx -d example.com -d www.example.com. Confirm HTTPS loads and that HTTP redirects to it.

  5. STEP 5Schedule backups and document billing per client

    Set up a scheduled database export and a file archive written to a folder outside the public web folder, then copy them off the server to storage the agency controls, since the official data does not confirm provider backups for this plan. Record where the backups go, who holds the SSH keys and the monthly cap for this server in the client's project documentation, so the per-client cost and recovery path are clear to anyone on the team.
