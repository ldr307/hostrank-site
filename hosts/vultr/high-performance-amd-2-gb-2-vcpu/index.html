What the official listing includes

The pricing page lists four resources for this plan: 2 vCPU, 2 GB of memory, 60 GB NVMe SSD storage and 4 TB of bandwidth. The hardware description is limited to the feature wording High Performance (AMD EPYC, NVMe SSD); the data contains no clock speeds, benchmark figures or disk throughput numbers, so any performance judgment has to come from your own load tests rather than from this page.

Because this is a self-managed server, the operating system, web server, runtime, database, firewall and updates are all yours to install and maintain. Vultr provides the virtual machine and the network; what runs on it is entirely under your control, which is the trade-off that makes a Cloud VPS flexible for custom app stacks.

How hourly billing up to a monthly price works

The billing field reads USD per month; billed hourly up to the monthly price. In practice, charges build up hour by hour while the server exists, and once they reach the monthly figure shown in the price table they stop growing for that cycle. The listed term of 1 month is the length of the cycle that the cap applies to, not a period you sign up for in advance.

The feature list calls this a flat monthly price (no intro discount), and the data records the renewal price as the same as the first-term price, so there is no promotional rate that later gives way to a different one. Keep in mind that the monthly amount in the table is the ceiling the hourly meter can reach in a cycle; it is not described as a fixed charge that lands on the account regardless of usage.

What the data does not say is how charges behave when a server is powered off or deleted. Anyone planning to spin up a short-lived server for a load test or a migration rehearsal should confirm with Vultr how stopped and deleted instances are metered before relying on that pattern.

Matching 2 vCPU and 2 GB to the app

Memory is usually the first constraint to size against on a plan with 2 GB. The operating system, the web server, the application runtime and any database on the same machine all share that allocation, so a single Node, Python, Ruby or PHP app process behind Nginx with a modest database is a different proposition from the same app plus a job queue, a cache daemon and a search index. A quick way to decide is to measure the resident memory of each process on a staging box under realistic traffic and add headroom for spikes before choosing this size.

The 2 vCPU allocation suits request handling that is mostly waiting on I/O, which describes many web apps. Workloads that compile assets on the server, resize images in bulk or run heavy background jobs will compete with web requests for the same two cores. If that is the plan, it is worth testing whether moving those jobs off the web server, or to a separate server metered on the same hourly basis, keeps response times steady.

Storage and transfer: 60 GB NVMe SSD and 4 TB

The 60 GB NVMe SSD volume has to hold the operating system, the application code, the database files, logs and any local backup copies. For an app whose data is mostly database rows and code, that is often comfortable; for an app that accepts large user uploads, planning to store those files in a separate storage service rather than on the root volume avoids a disk-full outage later.

At 4 TB, this plan lists more monthly transfer than the three Vultr alternatives covered below, each of which lists 3 TB. The data does not say what counts toward that figure or what happens if a month exceeds it, so confirm overage handling with Vultr if the app serves large downloads or video.

Resizing later

The official data does not confirm whether this plan can be resized in place to a larger size, whether the NVMe volume can be scaled down after growing, or whether a server can move between the High Performance, High Frequency and Cloud Compute families. Treat upgrades as an open question to confirm with the provider before choosing a size that leaves no room to grow.

A practical hedge is to design the deployment so that moving to a bigger server is a redeploy rather than a rebuild: keep Nginx and app configuration in version control, script the server setup, and keep a tested database export routine. With that in place, running the old and new servers side by side during a cutover is simply two servers metered by the hour, each up to its own monthly price in the table.

How the alternatives compare

Vultr Cloud Compute 2 GB / 2 vCPU lists the same 2 vCPU and 2 GB, with 65 GB SSD and 3 TB of bandwidth, and is described as Regular Performance (previous-gen Intel, regular SSD). It fits an app that needs a little more disk capacity and does not depend on NVMe or the AMD EPYC wording, with transfer comfortably under 3 TB.

Vultr High Frequency 2 GB / 2 vCPU keeps the 2 vCPU and 2 GB pairing but lists 80 GB NVMe SSD and 3 TB, described as High Frequency (3GHz+ Intel Xeon, NVMe SSD). It fits a workload that is happy with the memory size but wants more NVMe space, for example a database that is growing faster than the code.

Vultr Cloud Compute 4 GB / 2 vCPU doubles the memory listing to 4 GB and lists 80 GB SSD with 3 TB, again on Regular Performance (previous-gen Intel, regular SSD). It is the option to consider when the staging measurements show that memory, not CPU, is what runs out first. All three Vultr alternatives share the same billing wording, USD per month; billed hourly up to the monthly price, and the same flat monthly price (no intro discount) feature.

DigitalOcean Basic 2 GiB / 2 vCPU lists 2 GiB of memory and 60 GiB SSD, with a feature line of Flat monthly price (no intro discount). Its billing field reads USD per month equivalent; billing term and prepayment depend on plan, which is a different model from Vultr's hourly metering and should be read on DigitalOcean's own pricing page. The DigitalOcean listing does not include a bandwidth figure, and its memory and storage are given in GiB rather than GB, so the two sets of numbers are not directly interchangeable.

Practical setup guide

  1. STEP 1Create the server and record its address

    Deploy a server on the Vultr High Performance AMD 2 GB / 2 vCPU plan with the operating system image your stack expects, and write down the public IP address it is assigned. Log in over SSH, install pending updates, and create a non-root user with sudo rights and an SSH key so the root account is not used day to day. Nothing about data center choice or image lists is in the official data, so pick those from what Vultr's site shows at signup.

  2. STEP 2Install the stack and deploy the app

    Install Nginx, the application runtime and the database, then deploy the app from version control and confirm it responds over plain HTTP when requested by the server's IP address. Keep the setup commands in a script from the start so the same server can be rebuilt on a larger plan later without guesswork. Do this before touching DNS, so visitors never reach a half-configured machine.

  3. STEP 3Point the domain's A and AAAA records at the server

    At your DNS provider, create or update the A record for the domain to the server's IPv4 address, and add an AAAA record only if the server has an IPv6 address to use. Once the records are saved, confirm that the domain resolves to the new server from your own machine with this command, replacing example.com with your domain: dig +short A example.com. Wait until that returns the server's address before moving on.

  4. STEP 4Issue a TLS certificate once DNS resolves

    With the domain pointing at the server and Nginx serving the site over HTTP, install Certbot and request a Let's Encrypt certificate that is installed into the Nginx configuration automatically, replacing the placeholders with your own hostnames: sudo certbot --nginx -d example.com -d www.example.com. Check that the site loads over HTTPS in a browser afterwards and that HTTP requests redirect.

  5. STEP 5Harden, back up and note how billing works

    Turn on automatic security updates for the operating system and configure a firewall that allows SSH, HTTP and HTTPS and blocks everything else. The official data does not confirm a backup or snapshot feature for this plan, so set up scheduled database dumps and file archives that are copied off the server and test a restore at least once. For billing, remember that charges accrue by the hour up to the monthly price shown in the table on this page, and confirm with Vultr how stopped and deleted servers are treated before relying on that for cost control.

Frequently asked questions

  • Is there an introductory discount on this plan?

    No. The feature list states flat monthly price (no intro discount), and the data marks the renewal price as the same as the first-term price, so the monthly cap in the price table is the figure to plan around from the start.

  • Does the monthly price mean the same charge every month?

    Not necessarily. Billing is USD per month; billed hourly up to the monthly price, so the monthly figure is the most the hourly meter can reach within a 1 month cycle. See the billing section above for what to confirm about servers that are stopped or deleted partway through a cycle.

  • Which of the compared plans has more memory than 2 GB?

    Among the alternatives listed, only Vultr Cloud Compute 4 GB / 2 vCPU lists a larger memory figure at 4 GB. The others list 2 GB, or 2 GiB in the case of DigitalOcean Basic 2 GiB / 2 vCPU, which uses a different unit.

  • Can the server be used for a short load test rather than a whole month?

    Charges accrue by the hour up to the monthly price, so a server that exists for part of a cycle is metered for the hours it exists. How a stopped or deleted server is billed is covered in the billing section above and should be confirmed with Vultr first.

  • Is SSH or root access included?

    This is a self-managed Cloud VPS, so administering it over SSH with full control of the operating system is the normal way of working. Choose the operating system image, create your own users and keys, and manage the server directly.
