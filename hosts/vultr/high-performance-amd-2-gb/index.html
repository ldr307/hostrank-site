What the official data lists for this plan

The plan comes with 1 vCPU, 2 GB of memory, 50 GB NVMe SSD storage and 3 TB of bandwidth. These are the figures shown on the official pricing page, and they are the only resource numbers this page relies on. The official data does not include clock speeds, uptime figures, server locations or benchmark results, so none of those appear here.

The feature list names two things: High Performance (AMD EPYC, NVMe SSD) and flat monthly price (no intro discount). The first describes the CPU and disk class; the second means the price in the table is not a promotional first-term rate. Billing is listed as USD per month; billed hourly up to the monthly price, with a term of 1 month, which is the cycle of that monthly cap. The plan is a self-managed server, so you receive the machine itself rather than a managed hosting panel, and you install and run the application stack yourself.

How hourly billing up to the monthly price works

The billing field says charges accrue by the hour, and the total for a cycle is capped at the monthly price shown in the price table. The 1 month term is the length of that cycle; it describes how often the cap resets rather than a period you sign up for in advance. Because the feature list says there is no intro discount and the official data marks the renewal price as the same, the monthly cap you see in the table is the cap that applies in later cycles as well.

Billing by the hour wins over the phrase flat monthly price when the two seem to conflict: the monthly figure is the ceiling for a cycle, not a fixed charge that is the same every month regardless of use. The official data does not say how charges behave when a server is powered off, idle or deleted, so check that with Vultr before assuming that stopping a server changes what you pay.

Matching 1 vCPU and 2 GB to the app

For a web app, the vCPU count sets how much CPU work can run at the same time: request handling, template rendering, background jobs, database queries and TLS handshakes all compete for it. With 1 vCPU, a single CPU-heavy task occupies the only core, so apps that run queue workers or cron jobs alongside the web process should be profiled under realistic load before settling on this size. The official data describes the hardware class as High Performance (AMD EPYC, NVMe SSD) but gives no throughput or clock figures, so measure your own app rather than relying on labels.

Memory is usually the first limit a small server hits. A typical single-server web app has to fit the operating system, the web server, the application runtime, a database and any cache into 2 GB. Add up the resident memory of each process as measured in your own staging environment, leave headroom for the database page cache and for traffic spikes, and treat swap as a safety net rather than a plan. If the stack already needs more than that in testing, this size is likely too small, and the comparison section below lists options with different memory and CPU figures.

Storage and transfer: 50 GB NVMe SSD and 3 TB

The 50 GB NVMe SSD disk has to hold the operating system, the application code, uploaded files, the database, logs and any local backup archives. Database size and log growth are the usual surprises on a small disk, so check your current database footprint and set log rotation before launch. NVMe SSD is the disk class named in the feature list; the official data does not give IOPS or throughput figures for it.

Bandwidth is listed as 3 TB. For sizing, estimate the average response size multiplied by expected requests, plus asset downloads, API traffic and any backups you push off the server. The official data does not state over what period the 3 TB applies, whether inbound and outbound traffic both count, or what happens if the figure is exceeded, so confirm those details with Vultr if your app serves large media or expects heavy traffic.

It is billed the same way, USD per month; billed hourly up to the monthly price, with a 1 month term and no intro discount. It fits an app where the CPU and disk class matter less than the memory figure and where 2 TB of transfer is enough; this plan fits an app that benefits from the AMD EPYC and NVMe SSD class and needs 3 TB of transfer.

Vultr Cloud Compute 2 GB / 2 vCPU keeps 2 GB of memory and 3 TB of bandwidth but offers 2 vCPU and 65 GB SSD storage on the Regular Performance (previous-gen Intel, regular SSD) class. For an app that runs a worker process next to the web process, or that spends more time in CPU than in memory, the extra vCPU may be the more useful difference; for an app whose bottleneck is disk latency, the NVMe SSD on this plan is the difference to weigh. Billing and term are the same as this plan.

Vultr High Frequency 2 GB has 1 vCPU, 2 GB of memory, 64 GB NVMe SSD storage and 2 TB of bandwidth on hardware listed as High Frequency (3GHz+ Intel Xeon, NVMe SSD). It is billed hourly up to the monthly price with a 1 month term and no intro discount. It suits an app that stores more on local disk and transfers less; this plan suits an app that transfers more and stores less. The official data gives no benchmark for either CPU class, so do not treat the labels as a performance ranking.

DigitalOcean Basic 2 GiB lists 2 GiB of memory and 50 GiB SSD storage with a flat monthly price (no intro discount) and a 1 month term. Its billing field reads USD per month equivalent; billing term and prepayment depend on plan, which is different wording from the Vultr plans, so read DigitalOcean's own terms rather than assuming hourly accrual. The official data does not list a cpu count or a bandwidth figure for it, and its memory and storage use GiB rather than GB, so the units are not directly ranked against this plan here. It fits a developer who wants to stay inside the DigitalOcean ecosystem; this plan fits one who wants Vultr's hourly cap and the High Performance hardware class.

Practical setup guide

  1. STEP 1Create the server and record its IP address

    Deploy a Vultr High Performance AMD 2 GB instance with the operating system image you intend to run, and copy the public IP address Vultr assigns to it. Log in over SSH, create a non-root user with sudo rights, and install your web server, runtime and database before touching DNS. Keep in mind that charges accrue by the hour up to the monthly price from the moment the server exists.

  2. STEP 2Point the domain's A and AAAA records at the server

    At your DNS provider, create or update the A record for your domain and the www host so they point at the new server's public IP address, and add an AAAA record if you have an IPv6 address for it. Do this only after the app is running on the server, so visitors are not sent to an empty host. You can confirm what the domain currently resolves to by replacing example.com with your own domain and running: dig +short A example.com

  3. STEP 3Issue the TLS certificate once DNS resolves

    When the domain resolves to the server, request a Let's Encrypt certificate so the app serves HTTPS. If the server runs Nginx, replace example.com and www.example.com with your own hostnames and run: sudo certbot --nginx -d example.com -d www.example.com. Afterwards, check that plain HTTP requests redirect to HTTPS and that the app loads over the secure address.

  4. STEP 4Enable updates, a firewall and your own backups

    Turn on automatic security updates for the operating system and configure a firewall that allows SSH, HTTP and HTTPS and blocks everything else. Because the official data does not mention backups or snapshots for this plan, schedule your own database dumps and file archives and copy them off the server, remembering that transfers to external storage count toward the bandwidth you are sizing for.
