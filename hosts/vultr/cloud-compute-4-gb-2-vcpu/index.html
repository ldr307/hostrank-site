What the official data lists for this plan

The plan name is Vultr Cloud Compute 4 GB / 2 vCPU, the provider is Vultr and the category is Cloud VPS. The listed resources are 2 vCPU, 4 GB of RAM, 80 GB SSD storage and 3 TB of bandwidth. The features field contains two items: Regular Performance (previous-gen Intel, regular SSD) and flat monthly price (no intro discount).

The term is listed as 1 month and billing is listed as USD per month; billed hourly up to the monthly price. The renewal_vs_intro field is marked as same, which means the price listed for later billing cycles is the same as the starting price. Beyond these fields the data does not describe server locations, operating system choices, a control panel, provider-side backups, a provider firewall, IPv6 or support arrangements, so none of those are claimed on this page.

Who this plan suits

A developer with a side project or a small API usually wants a server with enough memory to run an application process, a database and a reverse proxy at the same time without constant swapping. With 4 GB of RAM and 2 vCPU, this plan has more memory than the 2 GB and 2 GiB alternatives in the data, which matters when a web app, a Postgres or MySQL instance and a few background workers all live on one box.

The 80 GB SSD is listed as regular SSD rather than NVMe, and the CPU is described as previous-gen Intel. For an API that spends most of its time waiting on the network, or a project where database size and memory headroom matter more than raw disk throughput, that trade may be acceptable. If disk latency or single-core speed is the bottleneck, the High Frequency and High Performance AMD alternatives below describe different hardware.

Because charges are billed hourly up to the monthly price, this plan also fits someone who wants to spin up a server for a short experiment, a staging copy or a load test and does not want to commit to a full month of charges up front. The data does not state what stops or lowers charges, so treat the monthly price as the cap for a billing cycle rather than assuming an idle server costs nothing.

How the hourly billing works

The billing field says USD per month; billed hourly up to the monthly price. In practice this means usage is metered by the hour, and the charge for a billing cycle grows with each hour until it reaches the monthly price shown in the table. The 1 month term is the length of that billing cycle for the monthly cap, not a commitment. The features field also mentions a flat monthly price, but since billing is hourly, the monthly figure should be read as the ceiling for a cycle rather than as a fixed charge that is always the same every month.

The renewal_vs_intro field is marked as same and the features include no intro discount, so there is no promotional first price that is later replaced by a different one. What appears in the table is the price that applies to a full month of usage in any cycle. The data does not state whether stopping, powering off or deleting the server changes charges, so confirm that with Vultr before relying on it to keep costs down.

What a self-managed server needs: SSH, updates, a firewall and backups

This is a self-managed server, so the operating system, the web server, the runtime for the project and every security control are the reader's responsibility. SSH is the normal way to administer a Cloud VPS of this kind; set up key-based login as soon as the server exists and disable password authentication once a key works. Keep a copy of the key somewhere safe, because losing it on a self-managed box means recovering through whatever console or rescue path the provider offers, which the data does not describe.

Updates come next. On a Debian or Ubuntu based system, enabling unattended security updates and scheduling a reboot window keeps the base system patched without manual effort. Application dependencies, container images and language runtimes still need to be updated by hand or by a CI job, since the provider has no role in them on a self-managed plan.

A firewall should allow only SSH, HTTP and HTTPS from the public internet and block everything else, including the database and any internal services such as a metrics endpoint. A host-based firewall like ufw or nftables handles this on the server itself. The official data does not list a provider-level firewall, snapshots or automatic backups for this plan, so check what Vultr offers before signing up and plan to run backups from the server regardless: a scheduled database dump plus an archive of the project files, copied to a location outside this server.

Bandwidth is listed as 3 TB. For a small API returning JSON responses that is a generous allowance, but a project that serves large downloads, media or heavy image assets should watch transfer usage. The data does not state what happens if the 3 TB figure is exceeded, so confirm overage handling with Vultr.

Practical setup guide

  1. STEP 1Create the server and record its IP address

    After signing up, create the Vultr Cloud Compute 4 GB / 2 vCPU instance, choosing the operating system image and location from whatever Vultr offers; the data does not list those options. Note the public IP address shown for the new server and add an SSH public key during creation if the provider's process allows it. Log in over SSH, confirm key-based login works, then disable password authentication.

  2. STEP 2Patch the system, enable updates and open the firewall

    Run the operating system's package update as the first command on the box, then enable unattended security updates so patches apply without manual intervention. Configure a host-based firewall that allows only SSH, HTTP and HTTPS and denies everything else, and verify the SSH rule is in place before enabling the firewall so the session is not locked out. Install the runtime, reverse proxy and database the project needs and bind the database to localhost only.

  3. STEP 3Deploy the project, then point DNS at the server

    Deploy the application and confirm it responds over plain HTTP using the server's IP address before touching DNS. Only then update the domain's A and AAAA records at the registrar or DNS host to point at the new server's addresses. To confirm the change has propagated from a local machine, replace the placeholder with your own domain and run: dig +short A example.com

  4. STEP 4Issue a TLS certificate once DNS resolves

    When the domain resolves to the server, install Certbot and request a Let's Encrypt certificate for the Nginx reverse proxy. Replace both placeholders with your own hostnames and run: sudo certbot --nginx -d example.com -d www.example.com Afterwards, confirm the site loads over HTTPS and that HTTP redirects correctly, and check that the automatic renewal timer Certbot installs is active.

  5. STEP 5Set up backups and review the billing cap

    Schedule a nightly database dump and an archive of the project files, and copy both to storage outside this server, since the data does not list provider-side backups or snapshots. Test a restore at least once so the procedure is known before it is needed. Finally, review the table for the monthly price that caps hourly charges in each 1 month billing cycle, and confirm with Vultr how stopped or deleted servers are charged.
