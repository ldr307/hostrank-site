Who this plan suits

This plan fits a developer who wants a self-managed cloud server for a side project, a small API, a webhook receiver or a staging copy of an app. With 2 vCPU and 4 GB of RAM, it gives more memory than the smaller Vultr plans listed below, which can help when an app runtime, a database and a reverse proxy share one machine.

The plan is listed with the feature "Regular Performance (previous-gen Intel, regular SSD)". That wording describes the hardware tier as Vultr presents it. Specific performance figures are not part of the official data, so plan to measure your own workload after launch.

According to the official pricing page, the plan lists these resources: 2 vCPU, 4 GB of RAM, 80 GB SSD storage and 3 TB of bandwidth. The features are "Regular Performance (previous-gen Intel, regular SSD)" and "flat monthly price (no intro discount)".

How billing works

Billing is listed as USD per month, billed hourly up to the monthly price. In practice, charges build up by the hour, and the monthly price in the price table acts as the cap for that billing cycle. The listed term of 1 month describes the cycle of that monthly cap, not a commitment.

The features mention a flat monthly price with no intro discount, and the renewal price is listed as the same as the intro price. Read that together with the hourly billing: the monthly figure is the ceiling, not necessarily the exact amount on every invoice. The official data does not describe which server states are or are not charged, so check Vultr's billing documentation if you plan to create and remove servers often.

What a self-managed server needs from you

On a self-managed Cloud VPS, you handle the server yourself over SSH with root access. That means you choose and maintain the software stack, apply operating system security updates, and configure a firewall that only allows the services you actually use, such as SSH, HTTP and HTTPS.

Backups are also your responsibility unless you confirm a provider service. A simple habit is to export your database and archive your app files on a schedule, then copy them somewhere off the server. Test a restore at least once so you know the backups actually work.

For an API, also plan how you will issue and renew a TLS certificate, how the app restarts after a reboot, and where logs go so you can debug problems without guessing.

Practical setup guide

  1. STEP 1Create the server and note its IP

    Create the server in your Vultr account and choose an operating system you are comfortable maintaining. Note the server's public IP address. Connect over SSH and confirm you can log in before changing anything else.

  2. STEP 2Harden access and enable updates

    Create a non-root user with sudo rights and use SSH keys for login. Turn on automatic security updates using the method your operating system provides. Set up a firewall that allows only SSH, HTTP and HTTPS, and confirm your SSH session still works before closing it.

  3. STEP 3Deploy the app and test it on the IP

    Install your runtime, database and a reverse proxy such as Nginx, then deploy the API or site. Test it using the server's IP address so everything works before any traffic moves. Make sure the app starts again automatically after a reboot.

  4. STEP 4Point DNS and issue a certificate

    Once the app is ready, point your domain's A record, and AAAA record if you use IPv6, at the server's IP address. After DNS shows the new IP, issue a TLS certificate; with Nginx and Certbot installed, run this and replace example.com with your domain: sudo certbot --nginx -d example.com -d www.example.com

  5. STEP 5Set up backups and track billing

    Schedule database exports and file archives, and copy them off the server. Run a test restore so you know the process works. Keep an eye on usage in your account, since charges build up hourly up to the monthly price shown in the price table.
