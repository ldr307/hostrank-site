What the official data confirms about this plan

The official pricing page lists four resources for Vultr Cloud Compute 4 GB / 2 vCPU: 2 vCPU, 4 GB of RAM, 80 GB SSD storage and 3 TB of bandwidth. The features describe the line as Regular Performance (previous-gen Intel, regular SSD), which is Vultr's own label for this family of servers, and note a flat monthly price (no intro discount).

Billing is listed as USD per month; billed hourly up to the monthly price. In plain words, charges build up hour by hour and stop climbing once they reach the monthly price in the table. The 1 month shown next to the plan is the cycle that this cap applies to; it is not a commitment you sign up for.

Because there is no intro discount, the renewal price is the same as the price for the first month. There is no promotional rate that ends later, so the figure in the price table is the figure to plan around.

The official data does not include benchmark results, uptime figures or performance numbers for this line. Any difference between Regular Performance and the other Vultr lines mentioned on this page can only be described by the hardware labels Vultr uses, not by measured speed.

Who this plan suits

This plan fits a developer who wants one server with enough memory to run an application runtime and a small database side by side. With 4 GB of RAM and 2 vCPU, a typical side project stack such as a web framework, a reverse proxy and a database can share the machine without the memory pressure that a smaller plan would bring. The 80 GB SSD leaves room for code, logs, uploads and database files, and 3 TB of bandwidth covers a small API that serves JSON responses to a modest number of clients.

It also fits someone who prefers to pay for a server by the hour while experimenting. Because charges build up hourly up to the monthly price, a short test deployment does not automatically cost a full month, which suits spinning up a staging copy or trying a new stack.

It is a less obvious fit if your workload is disk-heavy or you specifically want newer hardware. The features for this plan say previous-gen Intel and regular SSD, while the Vultr High Frequency and High Performance AMD lines list NVMe SSD. The official data gives no speed figures for either, so the choice comes down to whether the hardware label matters for your project and how the resources and price compare in the table.

Finally, this is a self-managed server. Vultr provides the machine; you install and maintain the operating system, the web server, the application and everything around it. If you want a provider to handle updates, security and backups for you, a managed hosting plan is a different category from this one.

How hourly billing up to a monthly price works

The billing line reads USD per month; billed hourly up to the monthly price. Each hour the server exists adds a charge, and the total for the cycle cannot exceed the monthly price shown in the table. A server that runs for the whole cycle reaches that cap; a server that exists for a shorter time accumulates less.

The feature list also mentions a flat monthly price (no intro discount). Read together with the billing line, that means the monthly amount is a ceiling on hourly charges, not a fixed charge taken in full each cycle regardless of use.

The official data does not say what happens to charges when a server is stopped, powered off or left idle, so do not assume that stopping a server reduces or ends charges. Confirm that behavior with Vultr before relying on it, especially for a side project you plan to switch on and off.

What a self-managed server needs: SSH, updates, firewall and backups

SSH access is how you will do everything on this server, from installing packages to deploying your API. Plan to add an SSH key when you create the server, disable password logins once key access works, and create a non-root user with sudo rights for day-to-day work. The official data does not list which operating system images are offered, so check that the distribution you want is available before signing up.

Updates are your responsibility on a self-managed server. After the first login, apply all pending package updates, then enable your distribution's automatic security update mechanism so patches are installed without you remembering to run them. For an API that may sit untouched for weeks, this matters more than it does for a project you deploy to daily.

A firewall should allow only the services you expose, typically SSH, HTTP and HTTPS, and reject everything else. The official data does not mention a provider-side firewall feature for this plan, so plan on configuring a host firewall inside the operating system and confirm with Vultr whether a network-level firewall is also available.

Backups are the piece most side projects skip and most regret. The official data does not confirm a backup or snapshot feature for this plan, so build your own routine: export the database on a schedule, archive the application files, and copy both off the server to object storage or another machine. Test a restore at least once; a backup you have never restored is a guess, not a safeguard.

Within Vultr, High Frequency 2 GB / 2 vCPU lists High Frequency (3GHz+ Intel Xeon, NVMe SSD), 2 vCPU, 2 GB of RAM, 80 GB NVMe SSD and 3 TB of bandwidth. High Performance AMD 2 GB / 2 vCPU lists High Performance (AMD EPYC, NVMe SSD), 2 vCPU, 2 GB of RAM, 60 GB NVMe SSD and 4 TB of bandwidth. Both are billed hourly up to the monthly price with a flat monthly price (no intro discount). Compared with the Regular Performance plan on this page, each has less RAM (2 GB rather than 4 GB) but lists NVMe SSD instead of regular SSD, and the AMD option lists more bandwidth (4 TB rather than 3 TB) with less storage (60 GB rather than 80 GB).

Which fits which situation: if your project needs memory for a database and an application runtime together, the two plans with 4 GB or 4 GiB of RAM are the ones to weigh against each other in the price table. If memory is less important than newer hardware labels or NVMe storage, the High Frequency and High Performance AMD lines are the ones to compare. If you expect very light traffic and a small footprint, the DigitalOcean 2 GiB plan is worth checking. None of this is a ranking; the official data has no performance figures, so the decision rests on the listed resources, the billing method and the prices in the table.

Practical setup guide

  1. STEP 1Create the server, add your SSH key and note the IP address

    During server creation, choose the operating system image and region you want and add your public SSH key so you never need a password to log in. Once the server is running, record the IP address Vultr assigns to it; you will need it for DNS and for your first SSH connection. Log in as the initial user, apply all pending package updates, and create a non-root user with sudo rights for everyday work.

  2. STEP 2Lock down access and turn on automatic security updates

    Configure the host firewall to allow SSH, HTTP and HTTPS and to reject everything else, then confirm you can still log in over SSH before closing your current session. Disable password authentication for SSH now that key access works. Enable your distribution's automatic security update mechanism so patches land even when you are not paying attention to the server.

  3. STEP 3Deploy the application, then point the domain at the server

    Install your runtime, reverse proxy and database, deploy the side project or API, and confirm it answers over plain HTTP on the server's IP address. Only then update the domain's A/AAAA records at your DNS provider to point at that IP. From your own machine, confirm the change has propagated by replacing example.com with your domain and running: dig +short A example.com

  4. STEP 4Issue a TLS certificate once DNS resolves to the server

    When the domain resolves to the new IP, install Certbot following the Certbot instructions for your distribution and web server. If you are using Nginx, request and install a Let's Encrypt certificate by replacing the placeholders with your own hostnames and running: sudo certbot --nginx -d example.com -d www.example.com. Afterward, load the site over HTTPS in a browser and confirm that the certificate will refresh automatically rather than expiring unnoticed.

  5. STEP 5Set up backups and keep an eye on hourly charges

    Schedule a database export and an archive of the application files, copy both off the server to object storage or another machine, and perform a test restore so you know the process works. If you intend to rely on a provider-side backup or snapshot option instead, confirm it exists for this plan before depending on it. For billing, remember that charges build up hourly up to the monthly price in the table, so watch your usage during the first cycle and confirm with Vultr how stopped or idle servers are charged.
